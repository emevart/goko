# D-0013: реплики событий через историю разговора без инструментов; загрузка воркера по числу job

- Дата: 2026-09-14
- Решили: агент (расследование после проверки голоса и веба в браузере, решения координатора); founder ревьюит
- Уточняет: спека, разделы 3 («Поток хода») и 9 («Озвучивание событий», «Промпт»); D-0011 (тапы в любом режиме)

## Контекст

Проверка голоса и веба в браузере на dev (ПК, 14.09) дала два дефекта.

**Первая сессия после старта воркера осталась без агента.** Диспетчеризация
в комнате была, job не было больше 3 минут, воркер заявки не получил. Вторая
сессия получила агента сразу.

- По умолчанию `@livekit/agents` 1.8 сообщает серверу загрузку CPU. Вне
  контейнера это CPU всей машины, в контейнере — CPU контейнера с делителем
  на все CPU хоста.
- Сервер LiveKit 1.13 выбирает воркер для job только при загрузке ниже
  `targetLoad` 0,7. Если подходящего нет, заявка не уходит и не повторяется.
- Агент типа JT_ROOM диспетчеризуется один раз, при создании комнаты. Вход
  участника его не запускает.
- Итог: комната, созданная в момент всплеска CPU (сборка vite, KataGo, старт
  процесса job), навсегда оставалась без агента.
- Бесплатный опыт с настоящим воркером подтвердил механизм:
  - под нагрузкой 7 потоков на 8 CPU job получили 0 комнат из 3;
  - без нагрузки — 3 из 3;
  - с загрузкой по числу job под той же нагрузкой — 3 из 3.

**Реплики на тапы не про позицию.** В той же партии на три тапа Гоко ответил:
«Давай, чёрные вперёд», «Ты же играешь чёрными, ходи первым», «Жду твой ход».
Свой ход не назван ни разу. Повтор пути без OpenAI показал, что `events.ts`
строил верный текст («человек сыграл дэ четыре, ты ответил ка десять»).

- Текст уходил только в `generateReply({ instructions })`. У Realtime это
  `response.instructions` одного ответа, в историю разговора он не попадает.
- В истории были только `start_game` и «Твой ход». Промпт требовал брать
  ходы только из инструментов и сразу применять ход человека через
  `play_move`. Модель верила истории и промпту.

Платный прогон (около 40 с Realtime, три тапа, три варианта):

| Вариант | Что сделала модель |
| --- | --- |
| Как в коде | `play_move` на точку, куда человек уже сходил: «Точка занята. Жду другой ход.» |
| Переписанная инструкция без записи в историю | Сыграла за человека выдуманный ход D5. Сервер его принял, движок ответил, партия испорчена |
| Событие system-сообщением в истории | «Аш шесть.», инструментов не вызывала |

Выборка — по одному ответу на вариант. Приветствие в том же прогоне сказало
«Давай начнём. Твой ход?» ещё до `start_game`: промпт приветствия предлагал
«назвать ход».

## Решение

**Загрузка воркера** (`apps/voice-agent/src/load.ts`, `main.ts`):

- `loadFunc` — `min(activeJobs / MAX_JOBS, 1)`, `loadThreshold` — 1.
- `MAX_JOBS` = 8. Сервер даёт job, пока загрузка ниже 0,7, поэтому одновременно
  идёт не больше 6 job (5/8 = 0,625 < 0,7 ≤ 6/8).
  - `MAX_SESSIONS` по умолчанию 3. Сверх них живут job брошенных комнат: до
    5 минут без телефона (`emptyTimeout`), до 15 минут после его ухода.
    Потолок 6 — запас вдвое.
  - Потолок конечен: цикл, плодящий комнаты, упрётся в 6 процессов job, а не
    в память cx23 (4 ГБ).
  - 0,7 × 8 = 5,6 — не целое: граница не зависит от округления.
  - Если `MAX_SESSIONS` поднимут выше 6, поднять и `MAX_JOBS`.

**Реплики событий** (`apps/voice-agent/src/event-speech.ts`, `events.ts`):

- Текст события пишется как факт: что произошло, что это уже на доске и
  какую реплику сказать дословно. Например: «Человек тапом на экране сыграл
  дэ четыре, ход уже на доске. Твой ответ ка десять уже на доске. Скажи
  вслух только: «Ка десять».» Формулировок, похожих на просьбу применить ход
  («человек сыграл …», «назови свой ход»), нет. Так написаны все реплики
  событий: тап, ответ движка после тапа и после таймаута, пас, ход соперника,
  отмена кнопкой, новая партия с экрана, «Продолжаем партию», итог,
  `retries_exhausted`.
- Текст кладётся в историю разговора system-сообщением «Событие с экрана: …».
  - В Realtime: копия подтверждённой сервером истории сессии
    (`realtimeLLMSession.chatCtx`), в неё одно сообщение, затем
    `await realtimeLLMSession.updateChatCtx`. Разница с сервером — один
    `conversation.item.create`, промис ждёт подтверждения
    `conversation.item.created`. Затем сообщение вставляется в историю
    агента, чтобы следующая сверка библиотеки его не удалила. Так сама
    библиотека добавляет реплику пользователя.
  - В конвейере `pipeline`: `agent.updateChatCtx` с копией истории агента.
- Затем `generateReply` с короткой инструкцией «ответь на последнее «Событие
  с экрана»» и `toolChoice: 'none'`. В ответ на событие модель не может
  вызвать инструмент и поставить камень за человека.
- Реплики идут по очереди, каждая ждёт конца воспроизведения предыдущей.
- Если история не синхронизировалась (ошибка или таймаут плагина 5 с),
  воркер пишет строку `[!]`, и текст события идёт в инструкцию ответа.
  `toolChoice: 'none'` остаётся.

**Промпт** (`apps/voice-agent/src/prompt.ts`):

- Новое правило: сообщение «Событие с экрана» — данные сервера, все ходы
  из него уже на доске. Ход человека из события не применять через
  `play_move`, реплику сказать дословно, свой ход — координатой.
- `play_move` сразу — для хода, который человек назвал голосом или текстом.
- Информация о партии — из инструментов и сообщений «Событие с экрана».
- Приветствие предлагает сыграть партию, не говорит, чей ход, и не просит
  сделать ход: партия может быть ещё не начата.

Отвергнуто:

- `agent.updateChatCtx` в Realtime. Он не ждёт отправки: ответ мог уйти
  раньше сообщения. И он сверяет с сервером всю историю агента: у вызовов
  инструментов там локальные id, и плагин на каждое событие удалял и заново
  создавал элементы истории.
- Пауза фиксированной длительности перед ответом: есть ожидание
  подтверждения сервера.
- `generateReply({ userInput })`: оно ждёт синхронизацию, но сообщение идёт
  с ролью `user`, и модель примет событие за слова человека.
- Только переписанная инструкция без истории: в прогоне модель сыграла за
  человека.

## Последствия

- Воркер больше не отказывается от job при реально загруженной машине. Для
  cx23 это приемлемо: Realtime считается в OpenAI, KataGo — в своём
  контейнере.
- Седьмая одновременная комната останется без агента так же молча:
  диспетчеризация по-прежнему не повторяется. Последний рубеж — подсказка
  веба «Гоко не пришёл». Повтор диспетчеризации в game-server в это решение
  не входит.
- Каждое событие добавляет в историю Realtime одно system-сообщение:
  контекст разговора и входные токены растут на событие.
- `[!]` Остаточная гонка: если в момент добавления события библиотека сама
  правит историю (результат инструмента по голосовой реплике), копия может
  не содержать новых элементов, и сверка их удалит. Реплики событий идут по
  очереди, совпадение редкое. Признак — модель не помнит результат
  инструмента сразу после тапа.
- В ответ на событие модель не может вызвать даже `get_position`: всё, что
  нужно для реплики, должно быть в тексте события.
- Путь `pipeline` покрыт unit-тестом, на живой модели не проверялся.
