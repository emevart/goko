# Гоко: голосовой соперник по го на физической доске

- Тип: architecture / product
- Дата: 2026-09-07
- Статус: одобрена founder'ом 07.09 «в целом»; правки того же дня по инфраструктуре (раздел 11), речи (раздел 9) и AI-first разработке (раздел 18) — на подтверждение
- Проект: отдельный репозиторий `H:\goko`, с оглядкой на интеграцию в sdamex (раздел 16)
- Провайдеры: OpenAI (речь и разговор), KataGo (позиция, ходы, счёт), LiveKit (медиа)

## 1. Цель и сценарий

Играть в го на физической доске 13×13 против голосового соперника, почти не
касаясь телефона. Телефон лежит рядом с доской, на экране доска и лента
диалога. Всё управление голосом: начать партию, назвать ход, спросить о
позиции, отменить, спасовать, сдаться. Соперник отвечает голосом, его можно
перебивать, он помнит каждый ход и понимает текущую позицию.

Второй, не менее важный смысл: **система для го, которой управляют агенты.**
Голос — первый интерфейс. Те же операции доступны по HTTP сейчас и через
MCP-сервер потом, чтобы другие агенты (Claude, Codex и т.п.) могли играть
против нашего движка, против человека или друг с другом.

### Сценарий одной партии

1. Открыть `https://goko.<домен>` на телефоне, положить рядом с доской. На экране
   пустая доска, под ней лента диалога, кнопка «Микрофон» (iOS не отдаёт звук
   без касания). Нажать.
2. «Давай партию». Гоко: «Давай. Каким цветом и на каком уровне?» — «Чёрными,
   десять кю». — «Хорошо, твой ход». На экране: «ход чёрных, 10 кю».
3. «Дэ четыре». Гоко: «Дэ четыре. Отвечаю кэ десять». Оба камня появляются
   на экране, последний ход подсвечен. Человек ставит камень Гоко на доску.
4. Ошибка распознавания: поставлен D4, сказано D5. «Нет, дэ пять». Гоко
   откатывает пару ходов, ставит D5, отвечает заново.
5. Перебивание: «Стоп, а кто впереди?» Гоко замолкает и отвечает по оценке
   движка, лучший ход не подсказывает, пока прямо не попросят.
6. Ход тапом по экрану: Гоко озвучивает ответ так же, как после голосового хода.
7. Не расслышал — лента: «Ты: дэ четыре. Гоко: кэ десять».
8. Конец: «Пас». Гоко тоже пасует. «Считаю. Белые впереди на четыре с
   половиной». Территория залита на экране. Не согласен: «Отмени, доиграем».
9. «Ещё одну, белыми, восемь кю». Новая партия, Гоко ходит первым.

Критерий готовности стадии 1: полная партия у настоящей доски, меньше пяти
касаний телефона (микрофон, изредка тап), и всё время ощущение, что говоришь с
соперником, который помнит партию.

## 3. Архитектура

```
                телефон (РФ, без VPN)
                ├── HTTPS  → Caddy → apps/web (статика)   +  /api/* → apps/game-server
                └── WebRTC → LiveKit (VPS) ←────────────────┐
                                                              │ участник-агент
apps/voice-agent (воркер LiveKit Agents, VPS) ────────────────┘
        │  WebSocket → OpenAI Realtime (gpt-realtime)
        │  HTTP → apps/game-server (операции), SSE ← события
        │
apps/game-server ──HTTP──→ apps/go-engine (KataGo analysis + обёртка)
        │
   data/games/<id>.json (снапшоты)

apps/mcp-server (стадия 2) ──HTTP/SSE──→ apps/game-server
```

Состав репозитория:

```
packages/protocol      zod-схемы операций, ошибок и событий; типизированный HTTP-клиент
packages/go-core       правила доски, разбор координат, площадь, группы, SGF
apps/game-server       сессии, партии, места, события, вызов движка, токены LiveKit
apps/go-engine         Dockerfile с KataGo и сетями + обёртка genmove/analyze/score
apps/voice-agent       воркер LiveKit Agents: инструменты, промпт, озвучивание событий
apps/web               одна страница: доска, лента, микрофон, тапы
apps/mcp-server        стадия 2: операции как MCP-инструменты
infra/                 docker-compose.yml, Caddyfile, livekit.yaml, .env.example, scripts/{bootstrap,deploy}.sh
scripts/               doctor.mjs, smoke.mjs, chat.mjs — проверки для агентов из CLI
docs/                  README (карта), NOW (фокус), decisions/, runbooks/, superpowers/{specs,plans}
CLAUDE.md, AGENTS.md   правила для агентов-разработчиков (раздел 18)
```

Телефон общается только с Caddy и LiveKit. К OpenAI ходит только voice-agent.

### Поток хода

Голосом: фраза «дэ четыре» → Realtime-модель вызывает инструмент
`play_move("D4")` → voice-agent шлёт `play` в game-server → сервер проверяет ход
через `go-core`, применяет, запрашивает ответ у go-engine, применяет ответ,
пишет снапшот, публикует `state.updated` → веб перерисовывает доску → сервер
возвращает агенту оба хода → модель говорит «Дэ четыре. Отвечаю кэ десять».

Тапом: веб шлёт тот же `play` → та же цепочка → voice-agent получает
`state.updated` с `by: "human"` и `via: "tap"` и просит модель озвучить ответ
(`generateReply` с инструкцией). Голос и тап проходят через один обработчик,
расходится только последний шаг.

## 4. Модель партии

### Координаты и доска

- Столбцы `A B C D E F G H J K L M N` (индексы 0–12, буквы `I` нет), строки
  `1–13` снизу вверх. Ход — строка вида `D4`, пас — `pass`.
- `board` — строка длины `size*size` из символов `.`, `B`, `W`;
  индекс `(row - 1) * size + col`, `col` от `A = 0`. Веб и ownership движка
  приводятся к этой же индексации. Длина `board` равна `boardSize²` — это
  инвариант схемы `GameState` в протоколе, а не только соглашение (D-0003).
- Разбор координат принимает `D4`, `d4`, `D 4`, кириллические двойники
  (`А→A`, `В→B`, `С→C`, `Е→E`, `Н→H`, `К→K`, `М→M`, `О→O`, `Р→P`, `Т→T`),
  отвергает `I` и
  выход за размер. Ошибка разбора — `invalid_coord`, не молчаливая подмена.

### Партия

```ts
GameSettings = { boardSize: 9 | 13 | 19 = 13, rules: 'chinese', komi: 7.5 }
Rank = '20k'..'1k' | '1d'..'9d'                     // по умолчанию '10k'
Seat = { controller: 'human' | 'engine' | 'external', rank?: Rank, label?: string }
Move = { n: number, color: 'B' | 'W', coord: string | 'pass', captured: number, at: string }
Result = {
  winner: 'B' | 'W', margin?: number,
  reason: 'score' | 'resign',
  score?: { areaB: number, areaW: number, komi: number, dead: string[], ownership: number[] }
}
GameState = {
  id, createdAt, revision: number,
  settings: GameSettings, seats: { B: Seat, W: Seat },
  status: 'playing' | 'finished',
  toPlay: 'B' | 'W', moves: Move[], board: string,
  captures: { B: number, W: number }, ko: string | null,
  consecutivePasses: number, pendingEngineMove: boolean,
  result?: Result
}
```

Коми только полуцелое: `x.5` от 0,5 до 13,5. Ничьей по счёту площади нет, у
итога всегда есть победитель. Другое значение в `settings` — `400 bad_request`.

Идентификаторы партии и сессии — base36 времени создания в миллисекундах плюс
12 hex-символов случайной части, сейчас 20 символов. Сервер принимает только
`^[0-9a-z]+$` длиной до 64 без имён устройств Windows (`con`, `prn`, `aux`,
`nul`, `com0–9`, `lpt0–9`): id — имя файла снапшота (D-0009). Сгенерированный
id, который уже занят существующей или создаваемой партией, генерируется
заново, до 8 попыток; исчерпание — `500 internal`, а не перезапись снапшота.

Партия нужна только на 13×13, но `boardSize` в схеме стоит, потому что
`go-core` и KataGo размер безразличен, а веб рисует любой размер из состояния.
Никакого отдельного «режима 9×9» и «режима 19×19» нет.

### Места

- `human` — ходы приходят от голосового агента или тапом с веба.
- `engine` — после каждого хода соперника сервер сам вызывает go-engine на
  ранге места. Ранг меняется операцией `set_rank`.
- `external` — ходы приходят по API от стороннего клиента с токеном места
  (стадия 2). В протоколе заложено с v1: место с этим контроллером в v1
  отклоняется ошибкой `unsupported_controller`, чтобы схема не менялась потом.

В v1 голосовой сценарий — `human` против `engine` в любом порядке цветов. Партия
`human` против `human` принимается: движок в ней не работает, стоимости нет.
Отклоняются при создании место `external` и партия с двумя местами `engine`:
`unsupported_controller`, у второй — `details: { black: 'engine', white: 'engine' }`
(D-0005).

### Сессия

Сессия = комната LiveKit + указатель на текущую партию. Нужна, потому что
голосовой агент и веб живут в одной комнате, а партий за разговор может быть
несколько («ещё одну»). Партия может существовать и без сессии (для MCP).

```ts
Session = { id, room: string, currentGameId: string | null, createdAt }
```

## 5. Протокол

Операции — HTTP `POST` с JSON, схемы в `packages/protocol` (zod), оттуда же
типы и клиент, которым пользуются voice-agent, web и mcp-server. Ошибки —
`{ error: { code, message, details? } }` с кодами ниже. События — SSE.

### Операции

| Операция | Маршрут | Вход | Выход |
| --- | --- | --- | --- |
| `create_session` | `POST /api/sessions` | — | `{ session, livekit: { url, token } }`; комнату с `agents: [{agentName: "goko", metadata: {sessionId}}]` создаёт сервер, токен только `roomJoin` (D-0001) |
| `session_new_game` | `POST /api/sessions/:sid/games` | `{ black: Seat, white: Seat, settings?, waitForReply?: boolean = true }` | `{ state, firstMove?, replyTimedOut?: true }`; сессия переключается, событие `session.game`; если первым ходит движок, его ход ждётся как в `play`, и `replyTimedOut: true` означает, что движок не успел ответить в отведённое время |
| `create_game` | `POST /api/games` | то же | то же (без сессии, для MCP); только при `ALLOW_SESSIONLESS_GAMES=1` (dev, smoke), иначе `400 bad_request` с `details.reason: 'sessionless_disabled'` (D-0012) |
| `get_game` | `GET /api/games/:id` | — | `GameState` |
| `list_games` | `GET /api/games` | — | сводки; только при `ALLOW_SESSIONLESS_GAMES=1` (dev, smoke), иначе `400 bad_request` с `details.reason: 'list_disabled'` (D-0012) |
| `play` | `POST /api/games/:id/play` | `{ coord, color?, expectedRevision?, waitForReply?: boolean = true, via? }` | `{ state, move, reply?: Move, replyTimedOut?: true }` |
| `pass` | `POST /api/games/:id/pass` | `{ color?, expectedRevision?, waitForReply?, via? }` | как `play` |
| `resign` | `POST /api/games/:id/resign` | `{ color, via? }` | `{ state }` |
| `undo` | `POST /api/games/:id/undo` | `{ expectedRevision?, via? }` | `{ state, removed: Move[] }` |
| `correct_last_move` | `POST /api/games/:id/correct` | `{ coord, waitForReply?, via? }` | как `play` |
| `set_rank` | `POST /api/games/:id/rank` | `{ color, rank }` | `{ state }` |
| `analyze` | `POST /api/games/:id/analyze` | `{ maxVisits? }` | `Analysis` |
| `score` | `POST /api/games/:id/score` | — | `Result` (без завершения партии; для «кто впереди по площади») |
| `render` | `GET /api/games/:id/ascii` | — | текстовая доска с координатами |
| `sgf` | `GET /api/games/:id/sgf` | — | SGF партии |
| `events` | `GET /api/sessions/:sid/events`, `GET /api/games/:id/events` | — | SSE |

Семантика:

- `play` с `waitForReply: true` (по умолчанию) ждёт ответ движка до 8 с и
  возвращает оба хода. Если ответ не успел — `replyTimedOut: true`, ход
  движка придёт событием. Для места `external` ответ не ждётся.
- `revision` растёт на каждое изменение; `expectedRevision` при расхождении
  даёт `409 revision_conflict` с `details.revision`. Так голос и тап не
  затопчут друг друга. Инвариант: каждый переход партии в `game.ts` (ход,
  пас, откат, сдача, итог счёта, ранг) двигает ревизию ровно на единицу; на
  этом держится сопоставление ответа движка с ожидающим его запросом. Коммит
  сервиса может содержать несколько переходов: `correct` — это откат и ход в
  одном коммите, и его событие `state.updated` показывает скачок ревизии на 2.
  Клиенты не должны ждать шага 1 между событиями.
- Схемы запросов строгие: неизвестное поле в теле — `400 bad_request`
  (`expectedRevison` с опечаткой иначе молча снимал бы защиту от гонки).
  Схемы ответов и событий нестрогие: старый клиент переживает новые поля
  (D-0002). `coord` в `play` и `correct_last_move` — строка от 1 до 8
  символов, длиннее — `400 bad_request`.
- `analyze` и `score` ограничены бюджетом сервиса: 10 с и 20 с на весь вызов;
  не успел — `503 engine_busy`. По дедлайну вызов движка отменяется, его
  поздний ответ не применяется (D-0010).
- Клиент из `packages/protocol` ограничивает ожидание ответа: `create_session`,
  `play`, `pass`, `correct_last_move`, `session_new_game`, `create_game` и
  `analyze` — 15 с, `score` — 25 с, остальные операции — 5 с; поток `events`
  без потолка. Потолок выше серверного ожидания (8 с ответа движка, 10 с
  создания комнаты LiveKit, бюджеты 10 и 20 с), чтобы клиент видел код сервера. Истёк — исключение с кодом `client_timeout`
  (`humanText` — «сервер не отвечает»); этот код рождает только клиент, в
  ответах сервера его нет. Вызов принимает свой `AbortSignal`: отмена снаружи
  даёт исключение с причиной сигнала, а не `client_timeout`. Долгоживущий
  сигнал (сессии, воркера) можно передавать в каждый вызов: после вызова
  клиент не оставляет на нём ни слушателя, ни зависимого сигнала.
- `via` (`voice | tap | api`, по умолчанию `api`) клиент передаёт сам; сервер
  кладёт его в событие как есть. По нему voice-agent отличает свой же ход от
  тапа и озвучивает только чужие.
- `resign` сдаёт партию за цвет `color`, очередь хода не важна. Сдаться можно
  только за место `human`: за место `engine` — `400 bad_request` с
  `details.reason: 'not_your_seat'` (`humanText` — «это не твой цвет»), и на
  ходе человека, и на ходе Гоко; за место `external` — `unsupported_controller`. В партии
  человек против человека сдаться можно за любой цвет.
- `undo` откатывает до предыдущего хода того же места, что ходит сейчас:
  человек против движка — два хода; если движок ещё думает — один ход человека
  и отмена ожидающего ответа. В `finished` по счёту — снимает оба паса и
  возвращает `playing`; это возврат партии в счёт, и он проходит лимиты партий
  (раздел 7). После `resign` — `409 game_finished`, сдача
  окончательна, дальше только новая партия.
- `correct_last_move` атомарен: откат пары, новый ход, новый ответ движка.
- Две подряд `pass` → сервер сам считает результат (раздел 8) и завершает
  партию событием `game.finished`.
- Движок сдаётся, если после 60-го хода его winrate ниже 3 % и отставание
  больше 25 очков — по данным ответа `genmove`, без отдельного запроса.

Коды ошибок: `invalid_coord`, `illegal_move` (с `reason: occupied | ko |
suicide`), `not_your_turn`, `game_finished`, `nothing_to_undo`,
`revision_conflict`, `engine_busy`, `engine_unavailable`,
`retries_exhausted` (серия повторов фоновой задачи исчерпана, раздел 7; только
в событии `error`, в HTTP-ответах не встречается; серия бывает и у автосчёта,
поэтому `humanText` — «движок не отвечает, нужно повторить», без слова «ход»),
`unsupported_controller`, `not_found`, `bad_request` (тело не JSON, не прошло
схему или больше 64 КБ — тогда `details.maxBytes`; сдача за место `engine` —
`details.reason: 'not_your_seat'`; партия без сессии при выключенном флаге — `details.reason: 'sessionless_disabled'`, список партий при выключенном флаге — `details.reason: 'list_disabled'`), `limit_reached` (превышен
лимит сессий), `rate_limited` (превышен лимит частоты запросов с адреса,
D-0012), `too_many_games` (превышен лимит незавершённых партий на сервере или на клиента, D-0012),
`unauthorized` (нет или неверный `X-App-Key` / `X-Engine-Key`),
`internal` (непредвиденная ошибка сервера). HTTP-статусы: 400 для
`invalid_coord`, `illegal_move`, `unsupported_controller`, `bad_request`; 401
`unauthorized`; 404 `not_found`; 409 `not_your_turn`, `game_finished`,
`nothing_to_undo`, `revision_conflict`; 429 `limit_reached`, `rate_limited`,
`too_many_games`; 500 `internal`;
503 `engine_busy`, `engine_unavailable`, `retries_exhausted`. Слишком большое
тело — тоже 400, а не 413: отдельного кода в таблице нет. Ключ проверяется
раньше размера тела. Ошибка схемы не из разбора тела (например, мусор от
движка) — 500 `internal`, а не 400.

Язык и санитизация ошибок (D-0007):

- `message` — по-английски, для разработчика и логов, без путей, стеков и
  текста чужих исключений. Человеку его не показывают и не озвучивают.
- Русский текст для человека строит клиент по `code` и `details`:
  `humanText(code, details)` из `packages/protocol` (таблицы `ERROR_TEXT`,
  `ILLEGAL_REASON_TEXT` для `occupied | ko | suicide` и
  `BAD_REQUEST_REASON_TEXT` для `not_your_seat | sessionless_disabled | list_disabled`, `TOO_MANY_GAMES_SCOPE_TEXT` для `scope: 'client'`).
- `illegal_move` несёт `details: { reason, coord }`, `invalid_coord` —
  `details.coord`, `not_your_turn` — `details.toPlay`, `limit_reached` и
  `too_many_games` — `details.max` (у лимита на клиента ещё `details.scope: 'client'`), `rate_limited` —
  `details.retryAfterSeconds` (то же число в заголовке `Retry-After`, не
  меньше 1), `bad_request` схемы — `details.issues`, `bad_request` сдачи за
  место `engine` — `details.reason: 'not_your_seat'`, `bad_request` партии без сессии — `details.reason: 'sessionless_disabled'`, `bad_request` списка партий — `details.reason: 'list_disabled'`.
- Событие `error` для непредвиденного исключения: `internal` /
  `internal server error` или `engine_unavailable` / `engine is unavailable`,
  без исходного текста.
- Граница движка: ошибки go-engine приходят с фиксированным `message` —
  `engine is unreachable`, `engine response does not match the protocol`,
  `engine responded with <status>` (все `engine_unavailable`), таймаут —
  `engine_busy`. Коды go-engine `engine_busy` и `engine_unavailable` проходят
  своим кодом; `unauthorized`, `bad_request` и `internal` превращаются в
  `internal` (500) с `message` `engine error: <код go-engine>`. `details`
  go-engine наружу не проходят, исходная ошибка остаётся в `cause` и в логе.

### Analysis

```ts
Analysis = {
  visits: number,
  winrateB: number,           // 0..1, шанс чёрных
  scoreLeadB: number,         // очки, положительно = чёрные впереди
  topMoves: { coord, winrateB, scoreLeadB, visits }[],   // для стороны на ходу, до 5
  ownership: number[],        // -1 (белые) .. +1 (чёрные), индексация доски
  groups: { color, stones: string[], liberties: number, ownershipAvg: number,
            status: 'safe' | 'unsettled' | 'dead' }[]
}
```

`groups` строит `go-core` по доске и ownership: `dead` при среднем владении
против цвета сильнее 0,6, `unsettled` при |владение| < 0,3, иначе `safe`.
Это то, из чего Гоко делает «твоя группа справа внизу выглядит слабо».

### События

```ts
'session.game'     { gameId }                              // сессия переключилась на партию
'state.updated'    { state, cause: 'play' | 'pass' | 'undo' | 'correct' | 'rank' | 'engine'
                                   | 'resign' | 'new' | 'sync',
                     by: 'human' | 'engine' | 'external' | 'system', via?: 'voice' | 'tap' | 'api',
                     humanFallback?: boolean }
                   // 'new' — партия создана; 'sync' — первое сообщение при подключении к потоку;
                   // humanFallback — только у хода движка (cause 'engine'): true, если ход взят
                   // из поиска, а не из человеческой сети. В ответе play его нет, только в событии
'engine.thinking'  { gameId, color }
'game.finished'    { result }
'error'            { gameId, code, message }  // code — из списка кодов; текст для человека — humanText(code)
```

Поток сессии шлёт `session.game`, затем события только текущей партии сессии;
при подключении первым сообщением идёт текущее состояние. Сервер сверяет
партию при отправке каждого события: поздние события прежней партии (ход
движка, `error`) в поток сессии не попадают, а `gameId` в `engine.thinking` и
`error` даёт клиенту вторую сверку. Новая партия в сессии отменяет фоновую
задачу прежней (ход движка, автосчёт): вызов движка обрывается, результат не
применяется. Статус прежней партии не меняется, её события идут только в её
поток. Прежняя незавершённая партия становится брошенной: она не в счёте
лимитов, отметка переживает рестарт, и при старте задача ей не ставится. Задачу
и место в счёте ей возвращает действие человека на этой партии или открытие её
потока, если возврат проходит те же лимиты, что создание партии: сначала общий,
затем лимит клиента, в чей счёт шла партия (раздел 7, D-0012). Сверх лимита
поток открывается, но партия остаётся брошенной и без задачи, а действие
отклоняется `429 too_many_games` до операции. Так же проходит лимиты возврат к
партии, устаревшей по времени (раздел 7). После рестарта задачу получает каждая незавершённая
партия без отметки с активностью за последние `SESSION_TTL_MS`.
Клиент при обрыве
переподключается и перечитывает `get_game`. Каждые 15 с поток шлёт
комментарий `: ping`. Сервер закрывает поток сам, если очередь неотправленных
событий превысила 1000 (медленный клиент), если сессия истекла и при остановке
сервера. При остановке поток закрывается сразу и в счёт текущих запросов не
входит; уже отправленное в буфер потока клиенту не дойдёт. Соединение, где
запись застряла на медленном клиенте, рвётся не по сигналу, а позже: когда
сервис закрыт и текущие HTTP-запросы дописали ответ, в пределах `SHUTDOWN_MS`
(раздел 7).

## 7. `apps/game-server`

Node 22, Hono, zod-схемы из `packages/protocol`.

- Партии в `Map`; каждая операция под мьютексом партии; после изменения —
  атомарная запись `data/games/<id>.json`: временный файл сбрасывается на диск
  до `rename`, на POSIX после `rename` сбрасывается и каталог. При старте всё
  загружается, кроме завершённых партий, у которых последний ход (или
  создание) старше 30 дней: их снапшоты удаляются (D-0012). Незавершённая
  партия, у которой последний ход, создание или возврат к ней старше
  `SESSION_TTL_MS` (по умолчанию 2 ч), считается брошенной; брошенной сразу становится и
  прежняя незавершённая партия сессии, в которой началась новая, — отметкой
  `data/games/<id>.abandoned` рядом со снапшотом. Брошенной партии при старте
  фоновая задача (ход движка, автосчёт) не ставится, её ставит действие
  человека на партии или открытие её потока (раздел 5), если возврат проходит
  лимиты партий.
- Автоматика мест `engine`: после `state.updated`, если на ходу `engine` и
  партия идёт — ставится задача `genmove` (`pendingEngineMove: true`,
  событие `engine.thinking`); результат применяется как ход `by: "engine"`.
  Повторная задача на ту же ревизию не ставится.
- Клиент go-engine с таймаутами genmove 10 с, analyze 8 с, score 18 с.
  Таймаут — `engine_busy`, недоступность — `engine_unavailable`, партия не
  портится. Повтор один и только у genmove: через 200 мс, если соединение
  оборвалось до ответа (отказ в подключении, сброс); на таймаут и ответ с
  ошибкой повтора нет. Каждый вызов принимает `AbortSignal`: отменённый вызов
  не повторяется, его результат не применяется. Правило «движок < клиент <
  сервис»: бюджеты go-engine (8/6/15 с, раздел 8) короче таймаутов клиента, а
  те короче бюджетов сервиса (раздел 5), чтобы внутренний уровень сдавался
  первым с осмысленным кодом (D-0010). Автосчёт не запускает второй `score`,
  пока предыдущий вызов не завершился.
- Серия повторов фоновой задачи (ход движка, автосчёт, запись снапшота) —
  D-0006. После отказа сервер шлёт событие `error` и повторяет задачу через
  паузы 5, 10, 20, 40 и 60 с, то есть шесть обращений; после последнего —
  одно событие `error` с кодом `retries_exhausted`, партия остаётся `playing`.
  Серию заново запускает мутирующее действие человека на партии (отметка
  исчерпания снимается до операции, задача ставится после неё) и открытие
  потока партии или сессии; действие `by: 'engine'` её не перезапускает. Счёт
  серии обнуляет любой удачный коммит (человека, хода движка, итога счёта);
  отклонённое действие, отказ записи и устаревший отказ его не меняют, идущую
  паузу правило не сокращает. Одна запись счёта на партию общая для задач
  движка и счёта. Отказ по устаревшей ревизии или после `close` не даёт ни
  события, ни паузы, ни счёта; после `close` пауз нет. Нелегальный ход от
  движка применяется как пас с `[!]` в логе.
- Остановка по SIGINT/SIGTERM. Потоки SSE закрываются сразу и в счёт текущих
  запросов не входят. Сервер перестаёт принимать соединения. Сервис
  обрывает фоновые задачи движка сигналом отмены и дожидается их выхода.
  Текущие HTTP-запросы дописывают ответ: счётчик
  отпускает запрос, когда ответ записан в сокет. Оставшиеся соединения, в том
  числе с застрявшей записью медленного клиента, рвутся после того, как сервис
  закрыт и текущие запросы завершились. Выход 0, когда закрыты сервер и
  сервис. Всё это в пределах дедлайна 25 с (`SHUTDOWN_MS`), иначе выход с
  кодом 1; повторный сигнал — выход 1 сразу; выход ровно один.
  Коды выхода: 2 — конфигурация (нет переменной, неверный `ENGINE_URL` или
  `LIVEKIT_URL`), 1 — не удалось загрузить партии или слушать порт. Отказ
  `service.close` — строка `[!]`, выход всё равно 0. Пустая переменная
  окружения считается не заданной.
- LiveKit через `livekit-server-sdk`: комнату `goko-<id>` создаёт сервер
  (`RoomServiceClient.createRoom`, `agents` с `agentName: "goko"` и
  `metadata: { sessionId }`, `emptyTimeout` 300 с, `departureTimeout` 900 с —
  комната ждёт возврата телефона 15 минут, агенты её не держат); токен
  телефона — только `roomJoin` на эту комнату, TTL равен TTL сессии (D-0001).
- Забор: заголовок `X-App-Key` для всех `/api/*`, значение из `.env`; веб
  получает его из своего конфига сборки. Это не аутентификация, а защита от
  случайных прохожих; настоящая авторизация — при интеграции в sdamex.
- Лимиты: не больше N активных сессий (env, по умолчанию 3), TTL сессии без
  событий 2 часа. Срок продлевают создание сессии, новая партия в ней, любая
  операция с `sessionId` в пути, открытие потока сессии, каждый его пинг и
  каждое событие её канала; чтение (`get`, список) не продлевает. Пока телефон
  держит поток, сессия живёт; истёкшая сессия закрывает свой поток (D-0008).
  Привязка партии к сессии снимается при удалении и истечении сессии и при
  смене партии в ней.
- Лимит частоты на `/api/*` (D-0012): 60 запросов в минуту на адрес; создание
  (`POST /api/sessions`, `/api/games`, `/api/sessions/:sid/games`) — ещё 10 за
  10 минут на адрес, общий счёт. Превышение — `429 rate_limited` с
  `Retry-After`. Лимит проверяется раньше ключа; поток SSE считается один раз,
  при открытии. Адрес — адрес сокета; с `TRUST_PROXY=1` — последний адрес
  `X-Forwarded-For` (его дописывает свой прокси). `TRUST_PROXY` включает только
  значение `1`, пробелы по краям не мешают; `npm run doctor` предупреждает
  `[!]`, если он не включён. Ключ — адрес IPv4 целиком, для IPv6 — префикс
  /64, IPv4-mapped IPv6 (`::ffff:a.b.c.d`) считается IPv4. Память лимитера
  ограничена.
- Не больше 20 незавершённых партий на сервере, считая создаваемые; лишняя —
  `429 too_many_games` (D-0012). Брошенные партии (последний ход, создание или
  возврат старше `SESSION_TTL_MS` на момент проверки, или брошенные сменой
  партии) в счёт не идут. Возврат к брошенной партии, сменой или по времени
  (действие или открытие потока), проверяет общий лимит и лимит клиента, как
  создание: в пределах лимита партия снова в счёте, и возврат считается её
  активностью; сверх лимита поток открывается без возврата, действие —
  `429 too_many_games` с теми же `details`. Так же проверяется откат (`undo`,
  `correct_last_move`) партии, завершённой счётом: владелец партии помнится и
  после счёта; партия без владельца — завершённая счётом или незавершённая
  вне счёта — при откате идёт в счёт адреса запроса, и он записывается
  владельцем. Текущая партия сессии не мешает созданию новой в той же сессии.
- Не больше 3 незавершённых партий на клиента (ключ лимита частоты; у партии
  сессии — владелец сессии, создавший её), те же правила счёта; лишняя —
  `429 too_many_games` с `details.scope: 'client'`. `POST /api/games` — только
  при `ALLOW_SESSIONLESS_GAMES=1` (dev, smoke), иначе `400 bad_request` с
  `details.reason: 'sessionless_disabled'` (D-0012). `GET /api/games` — под тем же
  флагом, иначе `details.reason: 'list_disabled'`: без списка id чужих партий не узнать.
- Тело `/api/*` — не больше 64 КБ.

## 8. `apps/go-engine`

Контейнер: KataGo (релизная сборка Eigen для CPU; на ПК founder'а — релизная
OpenCL-сборка для Windows на RTX 3060) + основная сеть + человеческая сеть +
обёртка на Node.

Обёртка запускает `katago analysis -config analysis.cfg -model <main>
-human-model <human>` и общается по JSON-строкам через stdin/stdout, очередь
запросов с ограничением параллельности, перезапуск процесса при падении с
экспоненциальной паузой, `GET /health` с именами сетей и длиной очереди.
Внутренний заголовок `X-Engine-Key`, значение сравнивается за постоянное
время (дайджесты SHA-256 и `timingSafeEqual`).

Поведение обёртки (D-0010):

- Бюджеты запроса внутри go-engine: genmove 8 с, analyze 6 с, score 15 с,
  отсчёт от вызова, а не от отправки процессу. Истёк — `503 engine_busy`.
  Бюджеты короче таймаутов клиента game-server (10/8/18 с, раздел 7).
- Клиент отключился — запрос снимается: из очереди сразу, из работы командой
  `terminate` KataGo; место освобождается для следующего.
- Тело `/v1/*` — не больше 64 КБ, больше — `400 bad_request`. Ключ
  проверяется раньше размера тела.
- KataGo обрабатывает один запрос за раз; очередь до 8, полная очередь —
  `503 engine_busy` сразу.
- Процесс KataGo упал — перезапуск с паузами 1, 2, 4, 8, 16, 30 с. Пока идёт
  пауза перезапуска, запросы получают `503 engine_unavailable` сразу, а не
  ждут в очереди.
- Прогрев до открытия порта: первый запрос к движку с потолком 300 с (первый
  запуск OpenCL-сборки тюнит ядра минутами). Не успел или отказ — строка `[X]`
  и выход с кодом 3. Сигнал во время прогрева — остановка KataGo и выход 0,
  без строки «прогрет». Сторожа молчания KataGo короче этого потолка нет:
  ложное срабатывание во время тюнинга дало бы вечный перезапуск.
- Без `KATAGO_BIN` или `ENGINE_KEY`, а также при `ENGINE_PORT` не целым числом
  от 1 до 65535 — строка `[X]` с именем переменной и выход с кодом 2. Пустая
  переменная считается не заданной.
- Не удалось слушать порт или сокет сервера упал — строка `[X]` с кодом
  ошибки, остановка KataGo и выход с кодом 1.
- go-engine и game-server выкатываются только вместе: `humanFallback` в ответе
  `genmove` обязателен, ответ без него game-server считает нарушением
  протокола (`engine_unavailable`).

| Маршрут | Вход | Выход |
| --- | --- | --- |
| `POST /v1/genmove` | `{ boardSize, rules, komi, moves: [["B","D4"],…], rank, maxVisits = 10 }` | `{ move, winrateB, scoreLeadB, humanPolicyTop: [{coord, prob}], humanFallback, ms }`; `humanFallback: true` — ход из основного поиска, а не из человеческой сети; доходит до события `state.updated` хода движка |
| `POST /v1/analyze` | `{ …, maxVisits = 50, includeOwnership = true }` | `{ visits, winrateB, scoreLeadB, moveInfos, ownership }` |
| `POST /v1/score` | `{ … }` | `{ ownership, dead: string[], areaB, areaW, scoreLeadB, winner, margin }` |

Выбор хода на ранге (в обёртке, чтобы алгоритм был виден и тестируем):

1. Один запрос с `overrideSettings: { humanSLProfile: "rank_10k" }`,
   `includePolicy: true`: приходят `humanPolicy` (политика игрока ранга) и
   `moveInfos` основного поиска.
2. В `humanPolicy` обнулить нелегальные (`-1`); пас обнулить, если лучший ход
   основного поиска — не пас; обнулить хвост с вероятностью ниже 0,5 %.
3. Нормализовать и сэмплировать при температуре 1. Если всё обнулилось —
   лучший ход основного поиска.

Счёт: запрос `analyze` с 400 visits и ownership, мёртвые камни — с владением
против своего цвета сильнее 0,6, площадь считает `go-core`, коми 7,5.

Нормализация: обёртка отдаёт winrate и scoreLead всегда с точки зрения чёрных
(в конфиге `reportAnalysisWinratesAs = BLACK`, поле так и называется
`winrateB`), а массив ownership перекладывает из порядка KataGo (строки
сверху вниз) в индексацию доски из раздела 4. Обе вещи закрыты контрактным
тестом на несимметричной позиции, потому что перепутанная сторона или
перевёрнутая доска не падают, а молча дают правдоподобный бред.

Сети: основная — `b10c128` (решение стадии 0 по замеру на VPS: genmove 260 мс,
analyze 886 мс, score 5283 мс при целях 2 с / 4 с / 10 с на 2 vCPU);
человеческая — `b18c384nbt-humanv0` (единственная). `b15c192` не мерили и не
берём: она тяжелее примерно вдвое на визит, а запас у `score` меньше
двукратного. Замеры и условия пересмотра — `docs/research/stage0-results.md`.

## 9. `apps/voice-agent`

`@livekit/agents` + плагин OpenAI, воркер с `agentName: "goko"`. На каждую
комнату: читает `sessionId` из метаданных диспетчеризации, открывает
`AgentSession` с `RealtimeModel({ model: "gpt-realtime", voice: "marin" })`
только после `ctx.waitForParticipant()` (D-0001), серверный VAD с
перебиванием, транскрипция входной речи включена (лента на экране и логи).
Подписывается на SSE сессии. Партию не хранит: каждая реплика о позиции —
результат инструмента. Отвечает голосом или только текстом — по режиму,
который выбрал человек (ниже, D-0011).

### Речь

Распознавание и синтез — внутри `gpt-realtime`: модель слушает аудио и
отвечает аудио, без промежуточного текста, поэтому ответ начинается через
сотни миллисекунд и его можно перебить на полуслове. Голос `marin`
(параметр одной строкой, русский поддерживает). Текст реплик для ленты —
транскрипция, которую Realtime отдаёт параллельно с аудио.

Запасной путь, если русский голос Realtime не устроит по качеству или цене:
конвейер `STT → LLM → TTS` того же фреймворка (`openai.STT` на
`gpt-transcribe`, `openai.LLM`, `openai.TTS` на `gpt-4o-mini-tts` с
инструкцией по тону). Инструменты и промпт те же, меняется только сборка
`AgentSession`; задержка выше на 0,5–1 с, зато голос настраивается
инструкцией и минута дешевле. Переключатель — `VOICE_MODE=realtime|pipeline`.

Стадия 0: основным режимом остаётся `realtime`. Петля собралась целиком
(комната, диспетчеризация, инструмент `play_move`, русские реплики), сборка
`AgentSession` с `RealtimeModel` и серверным VAD завелась без ухищрений.
Параметры VAD, на которых это проверено: `turnDetection` типа `server_vad`,
`threshold` 0,5, `prefix_padding_ms` 300, `silence_duration_ms` 500;
`semantic_vad` не сравнивался. `[!]` Качество русского голоса, перебивание и
цена минуты живой речью не проверены — это прогон founder'а; конвейер
`pipeline` пишется только по его итогам. Детали —
`docs/research/stage0-results.md`.

### Режимы «Голос» и «Чат» (D-0011)

Голос — основной способ, чат — запасной, тапы по доске работают в обоих.

- Режим — атрибут участника `goko.mode` со значением `voice` или `chat`.
  Веб выставляет его сразу после входа в комнату и при каждом переключении
  (`localParticipant.setAttributes`), `scripts/chat.mjs` входит с `chat`.
  Для этого токен телефона несёт право `canUpdateOwnMetadata`: только свои
  имя, метаданные и атрибуты, граница D-0001 не сдвигается. Нет атрибута или
  значение чужое — `voice`.
- Агент читает атрибут у участника после `ctx.waitForParticipant()` и
  следит за событием `ParticipantAttributesChanged`. В «Чате» выключает
  аудиовход и аудиовыход сессии (`session.input.setAudioEnabled(false)`,
  `session.output.setAudioEnabled(false)`, `@livekit/agents` 1.8): ответ
  уходит только текстом в `lk.transcription`, вход — `lk.chat`. В «Голосе»
  включает обратно.
- Известная цена: переключить Realtime на текст на лету нельзя (`modalities`
  задаётся только при создании модели), поэтому в «Чате» модель продолжает
  генерировать аудио и мы платим за аудио-токены. Пересоздавать сессию при
  каждой смене режима не будем: теряется разговор.
- Запасной путь, если звук в «Чате» всё же доходит до телефона: веб в «Чате»
  отписывается от аудиотрека агента; это делается всегда, не только при сбое.
- Отказ `setAttributes` страницу не ломает: агент остаётся в прежнем режиме,
  веб всё равно глушит звук у себя и выключает микрофон.

### Инструменты

| Инструмент | Что делает | Результат для модели |
| --- | --- | --- |
| `start_game({ my_color, rank, komi? })` | `session_new_game`; если человек белыми, движок ходит первым и его ход входит в ответ | `{ ok, gameId, youPlay, firstMove? }` |
| `play_move({ coord })` | `play` | `{ ok, yourMove, myMove, captured, toPlay, moveNumber, note? }` или `{ ok: false, reason }` |
| `correct_last_move({ coord })` | `correct_last_move` | как `play_move` |
| `pass()` | `pass`; если движок тоже пасует, приходит результат | `{ ok, myMove: 'pass' \| coord, finished?, result? }` |
| `resign()` | `resign` | `{ ok, result }` |
| `undo()` | `undo` | `{ ok, removed, toPlay, status }` |
| `get_position()` | `render` + последние 6 ходов + пленные | текст |
| `get_assessment()` | `analyze` (50 visits) | `{ leader, marginPoints, winrate, weakGroups: [{ color, where, status }], bestMoves }` — `bestMoves` модель раскрывает только по прямой просьбе |
| `set_rank({ rank })` | `set_rank` | `{ ok, rank }` |

Формулировки `note` на русском («ко: сразу забрать нельзя», «точка занята»),
чтобы модель не переводила коды.

### Озвучивание событий

- `state.updated` с `via: "tap"` → `generateReply` с инструкцией «человек
  сыграл D4 тапом, ты ответил K10, назови свой ход». Тапы работают в любом
  режиме: комментарий к ходу всегда приходит в ленту, вслух — только в
  «Голосе» (D-0011).
- Партия двух людей (D-0005): агент комментирует ход и выполняет команды за
  того, чей сейчас ход; сам в такой партии не играет.
- `state.updated` с `by: "external"` (стадия 2) → «соперник сыграл …».
- `game.finished` → объявить результат из события.
- `session.game`, созданная кнопкой на вебе → короткая реплика о новой партии.
- `error` → реплика по `code` из `humanText`, а не `message`. Для
  `retries_exhausted` сервер больше не повторяет сам. Серию заново запускает
  только мутирующее действие человека на партии или открытие потока (раздел 7,
  D-0006); чтение её не запускает. Поэтому голосовой агент на первой реплике
  человека после `retries_exhausted` переоткрывает поток сессии, а веб
  показывает кнопку «Повторить», которая переоткрывает SSE.
- Признак `humanFallback` агент берёт из события `state.updated` хода движка:
  в ответе `play` его нет.
- Переподключение к той же партии (обрыв потока или переоткрытие после
  `retries_exhausted`) не теряет ход движка, которого агент ждал после тапа
  или таймаута инструмента. `session.game` сбрасывает ожидание только при
  смене партии. `sync` знакомой партии сверяет последний ход с последним
  ходом, который поток уже показал. При `pendingEngineMove` ответ движка ещё
  впереди, и его озвучит событие хода. Прежнее ожидание остаётся. Без него
  агент ждёт, только если ход человека сделан в разрыве: ответ на уже
  показанный голосовой ход вернёт инструмент. Если в разрыве сходил движок,
  `sync` называет этот ход той же репликой, что событие хода движка. Ход
  человека в реплике берётся из позиции. Иначе ожидание снимается молча:
  например, отмена в разрыве оставила последним старый ход движка.
- Итог партии агент забывает, когда партия снова идёт: при `undo` или `sync`
  с `status: "playing"`. Сверка идёт по ревизии: событие с ревизией не новее
  той, на которой итог стал известен, устарело и итог не стирает. После
  отмены новый `game.finished` той же партии объявляется снова.

Результаты инструментов с `ok: false` несут `reason` — русский текст из
`humanText(code, details)`, а не `message` сервера (D-0007).

### Промпт (ядро, полная версия в коде)

> Ты Гоко, соперник по го. Говоришь по-русски, коротко, как живой игрок за
> доской. Любая информация о партии — только из инструментов: не называй ход,
> которого не вернул инструмент, не описывай позицию по памяти. Ход человека
> применяй сразу через `play_move`, не переспрашивай; если ход нелегален —
> одной фразой объясни почему. Свой ход называй координатой и ничем больше:
> «Кэ десять». Оценку позиции обсуждай охотно, но лучший ход подсказывай
> только по прямой просьбе. Не пасуй, пока пас не стал разумным. Если тебя
> перебили — замолчи и слушай. Столбцы произносятся: A «а», B «бэ», C «цэ»,
> D «дэ», E «е», F «эф», G «гэ», H «аш», J «джей», K «ка», L «эль», M «эм»,
> N «эн»; буквы I на доске нет. В аргументах инструментов всегда латиница.
> За человека ходи только по его прямой просьбе («сходи за меня на дэ
> четыре») и всегда называй этот ход вслух; размышление вслух («а не пойти
> ли мне на дэ четыре») ходом не считается (D-0004).

Реплики до двух предложений, если не спрашивают о позиции. Промпт знает, что
человек может писать текстом: отвечать так же коротко; реплики всегда видны в
ленте, в «Голосе» ещё и звучат. Приветствие —
`generateReply` сразу после `session.start` и применения режима, а не в
`on_enter`: иначе в «Чате» первое приветствие успело бы прозвучать вслух.

## 10. `apps/web`

Vite + React + TypeScript, одна страница, портретный телефон в приоритете.

- `Board` — SVG: сетка, хоси, координаты по краям, камни, метка последнего
  хода, при `finished` по счёту — заливка территории и пометка мёртвых.
  Тап = ближайший пункт → `play` с `via: "tap"`. Не ход человека — короткое
  сообщение «сейчас ход Гоко», запрос не шлётся.
- `ModeSwitch` — переключатель «Голос / Чат» (D-0011), по умолчанию «Голос».
  «Голос»: микрофон включён, Гоко отвечает голосом и текстом в ленте. «Чат»:
  микрофон выключен, звук агента не принимается, внизу поле ввода и
  «Отправить» — текст уходит в `lk.chat`, Гоко отвечает только текстом.
  Режим уходит агенту атрибутом `goko.mode` (раздел 9).
- `Transcript` — лента-диалог «Ты: … / Гоко: …» из текстовых потоков LiveKit
  (`lk.transcription`), без дублей: строка Гоко держится по `lk.segment_id` и
  дописывается кусками, реплика человека добавляется один раз — финальный
  сегмент (`lk.transcription_final = "true"`) по `lk.segment_id`. Свою строку
  чата страница добавляет сама: `lk.chat` отправителю не возвращается.
  Автопрокрутка, последние 200 строк.
- `ChatInput` — только в «Чате»: поле до 500 знаков и «Отправить»; кнопка
  активна, когда агент в комнате готов (атрибут `lk.agent.state` выставлен и
  не `initializing`). Ошибка отправки — сообщение, черновик остаётся.
- `StatusBar` — чей ход, номер хода, ранг, пленные; при `finished` — результат.
  После события `error` с кодом `retries_exhausted` — кнопка «Повторить»:
  переоткрывает SSE, открытие потока запускает серию повторов заново (D-0006).
  Тексты ошибок — только `humanText(code)`, `message` не показывается (D-0007).
- `Controls` — «Микрофон» только в «Голосе», маленькие «Пас», «Сдаться»,
  «Отменить».
- `NewGame` — «Новая партия» открывает выбор: цвет человека (чёрные / белые /
  случайно) и ранг Гоко кнопками −/+ по списку рангов протокола, «Начать».
  Только существующими полями `new_game`: `black`, `white`,
  `settings.boardSize` и `settings.komi` от текущей партии (без партии —
  13×13 и коми 7,5). Форы в протоколе нет, выбора форы нет. Гоко комментирует
  новую партию событием `session.game`.
- Первое касание страницы (кроме переключателя) входит в комнату по токену
  сессии и вызывает `room.startAudio()` для iOS; в «Голосе» ещё и включает
  микрофон. Комнат страница не создаёт (D-0001). Не удалось войти — сессия
  забывается, страница предлагает перезагрузку, доска работает тапами.
- Режим, цвет и ранг помнятся на телефоне в `localStorage` (ключ
  `goko.prefs`); чтение и запись — в `try/catch`, при любом исключении —
  умолчания («Голос», чёрные, 10k). Ответ `create_session` — в
  `sessionStorage`, чтобы перезагрузка не плодила сессии.
- Хуки: `useSession()` (создание сессии, вход в комнату, режим, микрофон,
  аудио-элемент, чат, лента), `useGame(sessionId, onLost)` (SSE с
  переподключением, первые события потока — текущая партия и её состояние; `not_found` —
  новая сессия; «Повторить»; тапы и кнопки).
- Стиль: несколько CSS-переменных, тёмная и светлая тема по `prefers-color-scheme`,
  цели касания не меньше 44 px. Без дизайн-системы и без библиотек UI.

Если голосовой агент в комнате отсутствует (упал, не задеплоен), страница
продолжает работать тапами в любом режиме: доска и кнопки ходят в game-server
напрямую, «Отправить» в «Чате» выключена.

### VPS

Одна виртуалка вне РФ: Hetzner cx23 (2 vCPU, 4 ГБ, 40 ГБ, ~€6,5/мес с НДС) в Хельсинки —
из РФ до дата-центра Hetzner TLS доходит, но домашние и сотовые провайдеры
могут душить поток к зарубежному IP после рукопожатия (RU→RU не режут).
Голосовую петлю с телефона без VPN стадия 0 проверяет из сотовой сети и из
дома. Если поток душат — RU-релей перед VPS (TCP-форвард 443: сигналинг и
TURN/TLS) или LiveKit на RU-VPS при воркере на Hetzner; решение фиксируется
в `docs/research/stage0-results.md`.
Замер стадии 0 уложился в цели раздела 8 с запасом 1.9–7.7x, движок остаётся
на этом же cx23, рескейл до cx33 (4 vCPU, 8 ГБ, ~€10/мес с НДС) сейчас не
нужен. Он остаётся запасным ходом: панель рескейлит только CPU/RAM без
переезда, действие обратимо. Поводы вернуться к нему — замер под полной
нагрузкой стадии 1 или переход на более крупную сеть.
Ubuntu 24.04, Docker, ufw. Домен — поддомены `sdamex.com` (решение founder'а
08.09): `goko.` (веб и API) и `goko-lk.` (сигналинг LiveKit и TURN); имена
задаются в `.env` как `WEB_HOST` и `LK_HOST`, без Cloudflare-прокси.

`infra/docker-compose.yml`: `caddy` (TLS автоматически; `goko.<домен>` →
статика web и `/api/*` → game-server; `goko-lk.<домен>` → LiveKit 7880 с
WebSocket), `livekit` (`network_mode: host`, конфиг по образцу
`media-vm/livekit.yaml.example` из sdamex, `auto_create: false`, TURN только
UDP 3478 в v1), `game-server`, `voice-agent`, `go-engine` (лимит `cpus`,
чтобы LiveKit и Caddy не голодали во время analyze). Открытые порты: 22, 80,
443, 7881/tcp, 3478/udp, 30000–40000/udp (relay-аллокации TURN,
`turn.relay_range_*`), 50000–60000/udp. Развязка 443 для TURN/TLS по
образцу sdamex — только если телефон в какой-то сети не соберёт звонок.

Секреты в `/opt/goko/.env` на VPS, в репозиторий не попадают: `OPENAI_API_KEY`
(только voice-agent), `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` (LiveKit,
game-server, voice-agent), `APP_KEY`, `ENGINE_KEY`, `WEB_HOST`, `LK_HOST`. Пример —
`infra/.env.example`. Личный VPN-сервер founder'а и его релей в РФ проект
не использует: там 2 vCPU, заняты порты 80/443/8443, а с августа он несёт
продовую нагрузку sdamex (LLM-relay).

Первичная настройка VPS — `infra/scripts/bootstrap.sh` (Docker, ufw, каталог
`/opt/goko`), запускается founder'ом один раз. Деплой —
`infra/scripts/deploy.sh`: `rsync` репозитория на VPS и
`docker compose up -d --build`. Запускает founder или агент по явной просьбе
в текущей сессии.

### Два режима маршрутизации API

Телефон всегда ходит на `https://goko.<домен>`. Caddy на VPS направляет `/api/*`
либо в контейнер `game-server` (prod-режим), либо на ПК founder'а по
Tailscale (`API_UPSTREAM=http://<tailscale-ip-ПК>:8787`, dev-режим). VPS
входит в tailnet founder'а узлом с тегом, ACL разрешает ему только порт 8787
на ПК. Переключение — переменная в `.env` и `docker compose up -d caddy`.

В dev-режиме game-server на ПК выпускает токены с диспетчеризацией агента
`goko-dev`, воркер на ПК регистрируется под этим именем, а воркер `goko` на
VPS остаётся не у дел. Промпт, инструменты и движок правятся и
перезапускаются на ПК за секунды, телефон ничего не замечает.

### Локальная разработка

- `npm run dev` поднимает game-server (`:8787`), go-engine (`:8788`, нативный
  KataGo через `KATAGO_BIN`; на ПК — OpenCL-сборка для Windows, без установки
  CUDA), web (`:5173`), voice-agent под именем `goko-dev`. Без `KATAGO_BIN`
  game-server идёт с `FAKE_ENGINE=1` (случайные легальные ходы); web и
  voice-agent запускаются, только если их пакеты уже есть. Без `ENGINE_KEY`
  пара game-server и go-engine получает разовый ключ на запуск. Остановка —
  Ctrl+C: каждый процесс ждётся не дольше 30 с, затем дерево гасится силой.
  На Windows дети запускаются в консоли терминала (`windowsHide: false`) и
  получают Ctrl+C сами; на POSIX dev шлёт SIGTERM их группам.
- `npm run smoke` не создаёт сессий и комнат: `/api/sessions` не вызывается,
  `LIVEKIT_*` у game-server — всегда заглушки, настоящие ключи из `.env` ему
  не передаются (D-0001).
- `LIVEKIT_URL` в dev указывает на LiveKit VPS: локального LiveKit нет,
  телефону всё равно нужен внешний адрес. Всё, кроме голоса с телефона,
  работает и без VPS: партия проверяется через HTTP, диалог — через
  текстовый канал (раздел 12).
- Голос с телефона: dev-режим Caddy → ПК, либо prod-режим после `deploy.sh`.

## 12. Тестирование

- `go-core` (vitest): захваты одиночные, групповые, у края и в углу; ко
  запрещено сразу и разрешено после хода в другом месте; самоубийство;
  площадь с мёртвыми камнями; разбор координат, включая кириллические
  двойники и отказ на `I`; SGF туда-обратно; property-тест — случайные
  легальные партии, ни у одного камня на доске нет нуля дыханий.
- `game-server`: фейковый движок со сценарием ходов; полная партия человек
  против движка; автосчёт после двух пасов; undo во всех состояниях;
  атомарность `correct`; `waitForReply` с таймаутом; `revision_conflict` при
  параллельных ходах; восстановление из снапшота после рестарта; SSE отдаёт
  состояние первым сообщением.
- `go-engine`: контрактный тест с настоящим KataGo, включается только при
  `KATAGO_BIN`: ход всегда легален, пас не выбирается на пустой доске,
  `humanPolicy` присутствует, счёт известной законченной позиции совпадает,
  winrate на позиции с явным перевесом чёрных больше 0,5 независимо от
  стороны на ходу, ownership на несимметричной позиции лежит в правильных
  клетках.
- `voice-agent`: тест-фреймворк LiveKit Agents с замоканным клиентом
  протокола: «дэ четыре» → `play_move("D4")`; «нет, дэ пять» →
  `correct_last_move("D5")`; «пас» → `pass`; «кто впереди» → `get_assessment`
  и ответ без лучшего хода (LLM-судья). Запусков мало: каждый стоит денег.
- `web`: тап в пункт → правильная координата, включая края; лента показывает
  обе стороны. Приёмка руками на телефоне у настоящей доски.
- Всё запускается из командной строки и заканчивается кодом возврата:
  `npm run check` (типы и unit, vitest по всем workspace'ам; линтера в v1
  нет), `npm run smoke` (поднимает game-server с фейковым движком, с
  `-- --real` — go-engine с KataGo, играет сценарную партию по HTTP, сверяет
  отказы по `code` и `details`, печатает `ascii`), `npm run doctor` (Node, `KATAGO_BIN`, сети, переменные
  окружения без печати значений). Это глаза агента-разработчика: экран
  телефона он не видит.
- Текстовый канал голосового агента: воркер принимает текст через text
  stream `lk.chat` (стандартный вход `RoomIO`) и отвечает транскриптом в
  `lk.transcription`. Скрипт `scripts/chat.mjs` входит в комнату участником,
  шлёт фразы («давай партию», «дэ четыре», «кто впереди») и печатает ответы
  и вызовы инструментов. Так агент проверяет диалог без микрофона и почти
  без денег; аудио-тесты с телефона — founder.

## 14. Риски

- **Распознавание букв.** Русские названия латинских столбцов непривычны
  («е» и «и», «бэ» и «вэ»). Митигация: таблица произношения в промпте,
  `correct_last_move`, тест на 30 фразах на стадии 0. Запасной словарь —
  «как в шахматах» или слова вместо букв.
- **Модель называет ход без инструмента.** Правило в промпте плюс экран
  показывает только серверную правду; расхождение видно в ленте. Если
  повторяется — принудительный `tool_choice` на фразы с координатой.
- **Человеческая сеть на 13×13.** Училась в основном на 19×19; ощущение
  ранга может плыть. Проверяем на стадии 0, при необходимости сдвигаем
  профиль на пару рангов.
- **CPU-задержка KataGo.** Цели в разделе 8; если не укладываемся — меньшая
  основная сеть, меньше visits в analyze или рескейл cx23 → cx33.
- **Мобильные сети РФ.** Если у оператора закрыт UDP — TURN/TLS на 443 по
  образцу sdamex. Если в «режиме белых списков» оператор душит TCP к
  зарубежному адресу — вход через дешёвый VPS в РФ с прозрачным
  TCP-форвардом на 443 нашего VPS (схема личного VPN founder'а). Дома по
  Wi-Fi TLS до Hetzner работает стабильно.
- **Русский голос Realtime.** Может звучать с акцентом или стоить дороже
  ожидаемого; запасной конвейер STT → LLM → TTS описан в разделе 9,
  решение на стадии 0.
- **VPS в tailnet.** Dev-режим даёт VPS доступ к порту 8787 на ПК; доступ
  ограничен тегом и ACL, при компрометации VPS тег снимается.
- **Стоимость Realtime.** Порядок — единицы долларов за час партии; точная
  цифра снимается по биллингу на стадии 0. Для продукта — лимиты (стадия 3).
- **Доступ OpenAI для аккаунта из РФ.** У founder'а ключи уже работают через
  relay sdamex; voice-agent на VPS ходит напрямую.

## 18. Репозиторий и разработка AI-first

Код пишут агенты (Claude Code и другие), founder ставит задачи, ревьюит и
принимает у доски. Репозиторий устроен так, чтобы агент за одну сессию мог
понять состояние, сделать шаг и оставить следующему агенту точку входа.

- **Точки входа.** `CLAUDE.md` — правила и команды (канон); `AGENTS.md` —
  указатель для других агентов; `docs/README.md` — карта; `docs/NOW.md` —
  фокус, открытые вопросы и следующий шаг, агент обновляет в конце сессии;
  `docs/decisions/` — журнал решений после спеки (`D-NNNN`);
  `docs/superpowers/specs` и `plans`; `docs/runbooks/`.
- **Всё из CLI.** Проверки раздела 12 — единственный способ узнать, что
  работает. Скрипты печатают `[OK]`/`[X]` и возвращают код. Шагов «открой
  браузер и посмотри» нет, кроме приёмки founder'ом у доски.
- **Агент — такой же клиент.** Агент-разработчик играет партию через
  `POST /api/games/:id/play` и читает `/ascii`; разговаривает с Гоко через
  `scripts/chat.mjs`. Стадия 2 добавляет MCP, и агент подключается к системе
  так же, как внешний игрок.
- **Границы.** Секреты — только в `.env`, в git — `.env.example` и
  указатели. Деплой, действия в Hetzner, DNS, tailnet и аудио-тесты (стоят
  денег) — по явной просьбе founder'а в текущей сессии. Личная
  инфраструктура founder'а в доках не описывается: ни адресов, ни хостнеймов.
- **Процесс.** Правка в существующем потоке — без спеки. Новая подсистема —
  brainstorming → спека → план (superpowers). Тесты до кода.
- **Стиль.** Доки и комментарии по-русски, код и идентификаторы
  по-английски, маркеры `[OK] [!] [FIX] [X] [WIP] [TODO]`, без эмодзи.
  Коммиты: `<область>: <что сделано>` по-русски.
- **Публичный репозиторий.** Лицензия — MIT, см. `LICENSE`. В истории git не
  должно быть секретов;
  `data/`, `models/`, `.env*` в `.gitignore`.
